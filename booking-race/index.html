Why it happens, and what the fix changes
  1. The race: check and insert are two steps. Both requests pass the check before either inserts. The fix here is a per-room lock around both steps; in Postgres the durable version is an exclusion constraint on (room, time range), so the database refuses the second row.
  2. Back-to-back meetings: inclusive bounds treat 10:00 as inside 09:00-10:00. Half-open ranges fix it.
  3. Double delete: a missing row is read as if it existed. It now returns 404.

Which of the three race fixes fits depends on your database and how many app instances you run.
